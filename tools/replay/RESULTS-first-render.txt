====================================

Later instrumentation note: a subsequent session audit found that JFR's default
class-loader inventory can stop Java threads for100ms+. These timing results used
that older profile and are not clean game-only FPS evidence. The observed named
class-load movement remains structural evidence; later capture profiles disable
inventory walks and analyzers include VM-operation spans before blaming SDL/Metal.

The first large measured flight hitch repeats near camera X=-160/Z=514 in the
copied saved world. Earlier captures put it at 174/156/202ms. This is roughly
3.8s into the westbound flight; it is not evidence about every pause during world
entry or before replay warmup. The trace includes ChestRenderer extraction,

ETF 7.2.6 and EMF 3.3.12 are visual feature mods, not separate optimization patches.

All runs completed with focus, route and stable setup checks passing. No native

Actual class-load evidence and shipping change
---------------------------------------------
Opt-in traceClassLoading records jdk.ClassLoad names, duration and requesting
stacks. Sampled caller methods from the previous investigation did not identify
all loaded classes. The first-chest trace exposed 19 stable named types missing
from the existing preload list: 9 vanilla/fastutil render helpers and 10 ETF/EMF
helpers. Hidden/generated lambda names are excluded. Examples include the chest
material enum, sprite coordinate expander, render groups/prepared types,
ETFTextureVariator/provider classes and EMFLODHandler.

Fork.16 prioritizes that small list before the existing boot list on the same two
background preload workers. Class.forName(name,false,loader) retains the existing
loading-only behavior. No static initializers are requested, no new worker pool,
no world/entity/buffer references and no texture/model options disabled. Optional
mod classes that are absent follow the existing skipped-class path.
mcopt.preload.firstRender=false disables the priority list; mcopt.preload=false
still disables all preloading. Requested/resolved/unavailable counters are exposed
to the development replay report. Resolved includes already-loaded classes.

Both candidate captures verified 19 requested/resolved, 0 unavailable. The disabled
control verified 0 requested. The candidate's target frame no longer contained any
of the 19 named class loads; it contained only generated lambda/method-handle loads.
This structural movement of loading work is stronger evidence than the variable
wall-clock timings. Runtime initialization/resource lookup can still occur there.

The full normal-recording candidate route still contained a 76ms cold-phase gap
elsewhere and a 148ms return-phase gap. This targets the repeated first-chest class
loading work, not all freezes or the separate pipeline-future waits.

ETF config finding
------------------
The installed ETF 7.2.6 class files reference enableCustomBlockEntities and
enableEmissiveBlockEntities only in ETFConfig itself; those legacy fields do not
control the observed rendering path. The active canDoCustomTextures/Emissive code
consults per-type override maps and the current state.entityKey(). The block-entity
key API returns registry identifiers. The diagnostic off run therefore set
entityRandomOverrides/entityEmissiveOverrides for minecraft:chest,trapped_chest,
ender_chest to false. All ETF settings were restored; the shipping run had the
original full entity features enabled. No ETF config workaround is shipped.
