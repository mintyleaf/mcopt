Other repeatable replay hitches, 2026-10-24
=========================================

The saved recordings contain repeatable first-use stalls beyond the first chest.
They are distinct from sustained LOD rendering cost and new-terrain generation.

Method
------
Same marker-owned isolated instance and immutable real survival-world fixture as
RESULTS-first-render.txt; user builds retained. Frozen starting LOD cache restored
before each run. RD12/simulation8, LOD192/N2048, two workers/Low population, 4 GiB
ZGC, VSync60, world target2880x1620. Warmup15s, hold5s, westbound10s at64 blocks/s,
eastbound return10s, same westbound pass10s, settle5s. No native sampler, external
attach diagnostics or GPU pass splitting. JVM/filesystem/driver caches and thermal
state remain nondeterministic. Timings are start-to-start frame gaps, not scanout.

Item-frame pipeline: camera X about -46, return phase
--------------------------------------------------
Across six earlier captures this frame took 123-211ms, consistently near the same
position. Final fork.16 took148ms; its render thread parked79ms in PipelineCache
waiting for compilation. The new first-use event identifies minecraft:pipeline/
item_cutout, the exact RenderPipelines.ITEM_CUTOUT object, missing from a cache
with222 entries. It is a different identity from the location-keyed registry's
entry. The origin probe confirms ordinary vanilla static construction, not a mod
creating a pipeline during flight.

Minecraft26.3 gives ITEM_CUTOUT, ITEM_CUTOUT_GLINT and ITEM_CUTOUT_GLINT_SPECIAL
the same location. ITEM_TRANSLUCENT_GLINT and its SPECIAL variant also share one
location. register() stores them in a location-keyed map; later variants overwrite
earlier ones. ShaderManager compiles the map's surviving values during reload,
while PipelineCache correctly keys compiled entries by object identity. Thus the
three earlier variants wait for compilation at their first actual draw.

Fork.17 supplements only ShaderManager's required compile batch with these three
identities if absent. The public registry, pipeline names, states and cache keys
stay unchanged. Existing reload executors handle compilation; no new worker pool,
render-time prewarm or compiled-object aliasing. Each variant owns its compiled
object and follows normal cache close/reload behavior. No name-based reuse that
could mix normal/glint shaders or double-close a native object.
This compiles three pipelines earlier, including glint variants even if unused
in a session; it is a bounded startup/cache cost, not a memory reduction.
mcopt.startup.completePipelines=false restores the vanilla loading batch.

Other first-use helpers: return camera X about16
------------------------------------------------
Earlier traced frames took79-90ms and loaded painting/custom-feature/leash helpers,
including ETF's ETFSprite. Actual asset tracing corrected a sampled-stack inference:
the synchronous SimpleTexture loads were the nearby horse's texture, horse armor
and lead, not a painting image. Those individual loads take roughly1-6ms here;
no global texture preloader or ETF feature disable is justified by that evidence.

Fork.17 adds15 stable named classes actually observed at these two first-use frames
to the existing19-name priority list. The same two preload workers use the existing
Class.forName(name,false,loader) path; absent optional-mod helpers are skipped.
The initial control resolved all34 names and the15 added named loads disappeared
from both target frames. Hidden/generated lambda creation and texture lookup/upload
can still occur when entities first become visible.

SDL event-pump pause remains
---------------------------
There is also a separate early-session native SDL_PollEvent pause, not a fixed
camera location. Older captures clustered near22s after world entry; the fixed
capture moves it to the stationary hold around19s. A fixed timer is not proven.
The two new baseline
captures show102ms wall/22ms thread CPU and78ms wall/17ms CPU in pollEvents. Most
of the interval is therefore waiting or descheduling; this does not identify the
underlying native/OS cause. ZGC pauses there were microseconds, not the long wait.
No SDL events are skipped, no macOS main-thread work is moved to a worker, and this
pause must not be counted as fixed by shader precompilation or class loading.

Replay instrumentation
----------------------
ReplayAsset identifies PipelineCache misses and TextureManager.registerAndLoad
calls, including asset names and requesting stacks. It is initialized before
warmup so the diagnostic itself does not add first-use class-loading cost.
ReplayClientWork adds wall/thread-CPU spans for pollEvents, which runs outside
runTick's frame span. AssetScan reports these events beside route coordinates;
ClassLoadScan accepts an explicit output path to avoid overwriting another ROI's
name list. All additions are confined to the development replay harness/tools.

------------------
PipelinePrecompileChecks uses the real26.3 pipeline objects: all five affected
variants appear exactly once, original entries/order remain, completion is
idempotent and the opt-out returns the original list. Core/harness builds and
the34-name bundle check pass.

fixture, options, graphics configs, save-directory identity and starting cache
file count/bytes. Only mcopt.startup.completePipelines=false changes in the control
config. Both enable actual class-load tracing, resolve34/34 priority names and
