Profiler inventory interference and corrected walk, 2026-10-24
=============================================================

Finding and correction
----------------------
The stock Java25 profile.jfc enables jdk.ClassLoaderStatistics everyChunk and
jdk.ThreadDump every60s, as well as periodic native-memory/library inventories.
In this modded JVM, JFR Periodic Tasks requested ClassLoaderStatsOperation at
safepoints, sometimes stopping Java execution for80-280ms. GCPhasePause events
alone do not reveal this: it is a different VM operation. A surrounding Java
MetalOperation can include the stop even when the actual native wait is short.

Example from the15-minute recording: a210.600ms Java nextDrawable span contains
only10.210ms of native wait; a206.284ms class-loader VM operation overlaps it.
Other class-loader stops reach258.619ms. This is recorder-induced interference,
not evidence that Metal's drawable acquisition itself took210ms. Earlier
SDL/driver-attribution statements and benchmark maxima need that qualification.

Capture and replay profiles now explicitly disable ClassLoaderStatistics,
ThreadDump, NativeMemoryUsage, NativeMemoryUsageTotal and NativeLibrary. Stack
sampling, sampled allocation, CPU/RSS/GC data, VM-operation events and Metal
telemetry remain. Thread/memory census walks are not needed for frame attribution.
No Minecraft restart or production mod rebuild is needed for a live JFR setting
change. The development replay harness is rebuilt with the same exclusions.

Do not apportion the overall improvement to a single cause or call this a direct
browser-only/recorder-only A/B. The disappearance of inventory VM stops is proven
independently by the events themselves.
